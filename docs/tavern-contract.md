# 酒馆接入契约：下一轮实施

本轮不修改 `sillytavern-general-battle-system`。通用框架与其数据结构隔离，以下是后续接入需要落实的映射。

| 酒馆侧事实／入口               | 框架接入点                              | 必须保留的边界                             |
| ------------------------------ | --------------------------------------- | ------------------------------------------ |
| 当前战斗、回合、单位激活       | `Observation` + `notify()`              | 每次事实改变递增状态版本                   |
| ally / enemy / neutral         | `Commander.side`、`Unit.side`           | 只控制明确授权的单位；中立不默认接管       |
| 单位状态、位置、HP、武器与资源 | `Unit` 和宿主特征                       | 宿主是权威，不从正文覆盖                   |
| 单位可用技能与移动             | `legalActions()`                        | 使用引擎原有 AP、LOS、距离、护甲与技能规则 |
| 原自动步进／停止入口           | `execute()`、`pause()`                  | 串行结算，维持已有异步界面响应             |
| 用户显式任务                   | `updateGoals()`                         | 优先级高于宿主补充与正文补齐               |
| 最近完成正文消息               | `NarrativeSource`                       | 默认六条，角色可筛选；读消息不发送新消息   |
| 原战报与玩家提示               | 宿主自己的呈现方式                      | 决策日志不自动发送给正文 AI                |
| 保存成功与落盘核实             | `PlanStore`、宿主回执                   | 不把候选状态冒充已保存状态                 |
| 手动行动                       | `manual()` 或先暂停冲突任务再由宿主结算 | 手动优先，取消过期模型结果                 |

后续适配必须实现持久化动作回执。`key` 和动作结算在同一持久化边界写入；收到重复 `key` 时返回原回执。仅依赖前端内存 Set 无法保证重启后去重。

核心不重新实现酒馆的直射／曲射、友军 LOS、濒死占位或护甲公式。宿主生成哪些动作合法，框架就在其中选择。

第一次联调顺序：只读取真实战场 → 本地规则影子决策 → 验证合法动作与回执 → 自动提交单步 → 暂停／手动介入 → 保存和重启 → 再开启连续循环与模型。接入前保留现有战斗状态的独立快照。

`configs/tavern.profile.example.json` 只有字段示例；其中单位 ID 必须替换，不能直接控制真实单位。
